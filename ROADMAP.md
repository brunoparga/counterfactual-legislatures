## Counterfactual legislatures - roadmap ##

This repo has the intent of examining what different countries' legislatures (usually lower house) would look like if they used a different electoral method. For FPTP countries (Canada, USA, UK, France, maybe Australia) the idea would be to show what they would look like under proportional representation. Countries that already have it could be tweaked; changing between D'Hondt and Sainte-Lague, for example. Spain could use autonomous communities instead of provinces as districts, and Brazil could let go of the minimum of 8 and maximum of 70 representatives per district. Thresholds could also be varied. Ideally we would have a function taking a country name, a desired system and election data for a given year and returning the detailed composition of its legislature. [Examples to add: Germany with only Erst- or Zweitstimme, before switching to proportional-past-the-post, and also what it would look like if it hadn't]

For a case like "proportional UK", for example, districts could be built on a constituent country basis, with England possibly split into its regions. Candidates from each region would be a list, with vote percentages in each constituency used to allocate party seats to individual candidates. [Inspo: the guys on Bluesky that compare the number of votes represented by Ayes and Nays at Westminster] [Also: an "index of representation" - what fraction of all voters voted nominally for the candidates that end up elected?]

This project explicitly acknowledges that it cannot account for the changes in party and voter behavior that would arise from the hypothesis of different voting methods, or the political feasibility of the changes.

A later phase of the project involves examining the impact of legislature changes on policy and its downstream consequences. There are two sources for that; one is policy-to-effect and the other effect-to-policy. The former would look at concrete cases of relevant political votes that happened in the real-world versions of these legislatures, identifying the ones where the counterfactual result of the vote is different, and then estimating the impact of the (non) adoption of the policy in question. The latter would search the literature for instances of the class "when policy A is implemented, variable X changes by this much", and then look for examples of such policies being voted on in the legislatures in question.

A preliminary phase involves building up-to-date versions of the [Shortest Splitline Algorithm](https://www.rangevoting.org/SplitLR.html) maps for the 2010 and 2020 US Censuses. Hopefully the data can also show how many people change districts between cycles (although the question of what constitutes the "same" district is not obvious).

Maps come in two flavours: state-by-state (each state gets its apportioned number of seats and is split independently, as the original autodistrict did) and all-48-in-one-go (the contiguous states as a single region, 432 seats, state lines ignored entirely). State-by-state, DC simply gets no map — it has no seats, so there is nothing to split. It only poses a question nationwide, where its territory sits inside the hull and would otherwise leave a hole: there it is drawn, but with its population zeroed, matching its lack of a voting House member. [Counterfactual worth generating once the pipeline works: the nationwide-in-one-go map *as if DC had a seat* — include its population and add a district. Because a national splitline map ignores state boundaries, changing the population field at all reshuffles every cut downstream of DC, so this should be pretty chaotic rather than a local edit around the Potomac. The main repo already has a Gleam implementation of Huntington-Hill, which can settle the honest version of the question: whether DC's seat comes out of some state's allocation with the House fixed at 435, or the House simply grows to 436.]

This and potentially other districting algorithms might be used to create single-member maps for countries currently using PR. Denmark has its nomination districts for that.

Once the block-level population data is in hand it costs nothing extra to re-apportion the House at sizes other than 435, and then draw the maps that follow. The obvious candidates are the cube root rule (House size is the cube root of the population, so roughly 692 seats on the 2020 count) and the Wyoming rule (every district holds about as many people as the smallest state, so roughly 574 seats on 2020), but the size should just be a parameter — 435 is an arbitrary freeze from 1929, and the point is to see what varying it does. Huntington-Hill (already implemented in Gleam in the main repo) gives the per-state allocation; the splitline engine takes a seat count per state and does not care where it came from. Worth pairing with the representation index above: a bigger House changes how many voters are on the winning side, not just how many members there are.

[Document the engine's input formats, so the districting code is reusable beyond the US. Nothing in the splitline engine is American: it takes an outline and a set of weighted points and returns a tree of cuts. All the US-specific knowledge lives in the converters — PL 94-171 offsets, SF1 offsets, FIPS codes, Huntington-Hill — and none of it is needed to district Denmark's nomination districts or to draw single-member maps for a PR country. Two formats are all an outsider needs: the boundary, in ARC/INFO ungenerate (polygon id and centroid, then vertex pairs, then END; -99999 starts a hole ring; a final END closes the file), and the population points, as `tract,block,pop,curve,lon,lat,area_m2` where only population, longitude, latitude and area are actually read — the first two columns are inherited labels and `curve` is vestigial. Worth writing that down properly, and probably worth renaming the columns to something not borrowed from the US census while we are at it, since a Danish user should not have to supply a "tract". The same document should state what the engine assumes: that coordinates are degrees, that the projection is gnomonic centred on the outline's bounding box, and that population is spread over an equal-area disc rather than a real block polygon.]

[Split rendering out of the engine first, because everything else in this section depends on it. The picture is already a pure function of the cut tree, but today it is drawn inside the same process that computes the tree, so changing a colour means re-running the districting. A standalone renderer that reads a tree JSON plus a boundary would make every visual change cost seconds instead of hours, and makes the animation and the stitcher fall out almost for free. Probably a `--render-only` mode on the existing engine, loading the tree from JSON instead of computing it, rather than a second implementation of the scanline fill.

Then: a rendering that reproduces the CRV maps as closely as we can, from our own runs rather than by copying theirs. Three known differences. (1) Their nationwide maps use six colours — grey, red, purple, blue, green, gold — where we use four; six makes the graph colouring easier, not harder, so this is just a palette swap plus letting the search use the extra colours. (2) Their cut lines continue past the land all the way to the image border, drawn in a colour taken from the region the cut just created — visible around southwestern Virginia. Ours stop at the coastline. Since the tree stores every cut as an infinite line and only the drawing clips it, extending them is a few lines. (3) Their maps are darker: the 2007 renderer scales brightness linearly as `pop * 60 / min(10000, max_pop)` and adds it to a base of 192/255, so only genuinely dense pixels brighten at all, whereas ours uses a log curve that lifts moderate density much too much. Matching means going back to linear with a high cap. After that we want a second, modern-looking rendering from the same trees — which is exactly what the standalone renderer buys.

[Animation: the tree already contains it. Frame N is the same map with only the first N cuts applied, so a whole state or the nation can be shown splitting one cut at a time, depth-first, with no recomputation — truncate the tree, treat every unsplit node as a single district, render. Worth doing at both scales: a state is a short clip, the 432-district nationwide map is a long one that shows the recursive halving very clearly.] — the state name, or "contiguous United States" for the all-in-one-go map, and the number of seats. Worth including the census year too, since the same state appears three times with different populations and sometimes a different seat count. Where the seat count comes from something other than the ordinary 435-seat apportionment, say so on the map: "574 seats (Wyoming rule)", "692 seats (cube root rule)". Only when applicable — an ordinary map should not be cluttered with "(435-seat apportionment)". This should not be a closed enum of rules, because the DC-with-a-seat map above is a one-off rather than a rule, and any later one-offs will be too; what travels with the seat count is a free-text provenance. Right now the runner takes a seat override with no record of why, so that provenance has to be threaded through before the label can report it. Probably better done in the Python layer, where PIL is already available, than in the engine, which currently has no font handling and is nicer for not needing any.

The label should be placed by looking at the map rather than dropped in a fixed corner. States are not rectangles, so most of them leave a large hole inside their own bounding box: Maryland has a great empty wedge where Virginia and West Virginia are, and the caption belongs there. The land mask already exists, so this is the largest-empty-rectangle problem on a binary image, which the largest-rectangle-in-a-histogram trick solves in one pass per row. Score candidate rectangles by how big the text can be drawn inside them rather than by raw area, or a long thin slot wins and is useless. Near-rectangular states — Colorado, Wyoming — have no interior hole worth using, so the fallback is to extend the canvas and caption outside the outline rather than print over land. The same "where is the empty space" machinery would place the city inset boxes below, and a legend if we ever want one.]

[Rendering: go back to the original four colours. Sampling CRV's published maps, the palette is exactly four hue families — teal (0,G,B), green (0,G,0), purple (R,0,B), olive (R,G,0) — with the channel value carrying population density, from about 32 where nobody lives up to 255 in the densest blocks. That is why those maps read as dark with bright city speckle, and it is worth keeping: it puts two variables on one image, districts and where the people actually are. Four is not just aesthetic either. A map of contiguous regions is a planar graph, so four colours always suffice; greedy assignment does not find such a colouring on its own, so this wants DSATUR with backtracking. One caveat: splitline districts can be disconnected, as in Hawaii where one district spans separate islands, and that breaks planarity — so the code needs a documented fallback to five or more rather than failing. Note the point-based engine no longer rasterises population at all, so the brightness channel means binning the points into the render canvas; that is cheap and needed only for drawing, not for the search.]

[Colour the stitched map by applying the four-colour theorem twice, once at each level. Give every state one of four main colours from a four-colouring of the state adjacency graph, then give that state's districts four shades of its own colour from a four-colouring of the district adjacency graph inside it. State identity stays readable at a glance while districts remain individually distinguishable, which a flat colouring of 435 districts cannot do. The inner shades want to be as far apart as a single hue allows — vary lightness and saturation together rather than lightness alone, or the four shades collapse into a gradient. One thing to watch: districts that are adjacent across a state line get their colours from different outer families, so they will contrast, but two districts of neighbouring states could still land on similar shades; if that reads badly, the inner four-colouring can take the cross-border neighbours into account as constraints.]

[A complete map of the US with every state districted separately, stitched into one image — distinct from the all-in-one-go map, since this one keeps state lines. Every state's tree carries its own gnomonic projection parameters, so stitching is: pick one national projection, and for each pixel go to lon/lat, work out which state contains it, then walk that state's tree. No re-running of anything, just a compositor over the trees we already have. Worth doing for all three censuses so the cycle-over-cycle comparison has a national view. The 2010 data is already complete, so this is buildable now.]

[Rendering: big cities need inset boxes. Population is what determines district size, so a metro area ends up as a knot of slivers that is illegible at whole-state scale while most of the map is a handful of enormous rural districts — Denver and Anchorage already show this, and it gets worse the more seats there are. The fix is a zoomed inset per major metro, drawn from the same cut tree at a higher resolution and keyed back to a box on the main map. Choosing which areas get an inset should fall out of the data rather than a hardcoded city list: look for districts whose area is far below the state median, cluster the adjacent ones, and box the cluster.

This pairs with the district numbers: label each district exactly once across the whole figure, in whichever view can actually show it. Districts big enough to read at whole-state scale get their number on the main map; the metro slivers get theirs only in the inset, which is the one place they are legible. That avoids both failure modes — numbers crammed illegibly into slivers, and the same number printed twice in two views. It also means the criterion for "needs an inset" and the criterion for "cannot be labelled in place" are the same test, so they should share an implementation rather than being tuned separately.]

[Also worth trying: compiling the splitline engine to WebAssembly so a reader can redraw the map in their own browser. The engine is portable C with zlib as its only dependency, so the compile itself is not the hard part — the data is. A national run needs something like 8 million block points, which is not going in a web page; a single state is far more plausible (Colorado is only ~84k populated blocks). So the realistic version is per-state redistricting client-side, with the nationwide map precomputed. Note that *looking up* a district needs none of this: the cut tree is a few tens of KB and the lookup is a handful of comparisons, so an address-to-district page is already feasible without WASM.]
